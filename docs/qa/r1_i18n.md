## Verdict

The i18n layer is in very good shape. Every reviewed string is on the page in all 16 variants. No Latin digit leaks
into hi, mai or bn. Shaping is clean. Routing and `?side` / `?reception` behave as the spec says on both hosts and
in all three engines. Two P2s are left:

- **I1**: on phones, the language switch loses up to 191 px of the place in the lower sections.

## Findings

### I1 (P2): on phones the language switch does not keep the place lower on the page

- **Where:** `src/state/place.ts` `restorePlace()`, called once from `LangLayout` `useIsomorphicLayoutEffect([lang])`.
- **Seen:** WebKit 390x844 (iPhone 14 emulation): 6 of 20 switches missed the 10% vh tolerance, all in the lower
  sections:
  - en->bn: Cultures 97 px, Venues 116 px, Closing 171 px.
  - mai->en: Cultures 88 px, Venues 115 px, Closing 191 px.

  Chromium 390 and Firefox 390 miss on Closing for hi/mai->en (114 px). Desktop is fine, apart from WebKit 1440
  en->bn Closing (95 px).
- **Why (measured):** the restore lands exactly at first, then the page keeps re-laying out under it. For WebKit en->bn
  the probe read `scrollHeight` 11611 px at 30 ms and 11861 px at 150 ms, with the Venues top moving from -158 to
  +93. The same happens on a second round in a fresh document, so it is not a cold HTTP cache. It is the target
  script's faces swapping in (`font-display: swap`, not loaded in this document) plus the new copy's line counts.
  Deep links have a 6 s pin (`PIN_MS`) that re-applies the jump on every resize. The switch has none.
- **Fix:** after `restorePlace()`, hold `{ id, ratio }` the same way the deep-link pin does. Use a ResizeObserver on
  `#main` plus `document.fonts.ready`, and release on wheel/touch/key or after ~2 s. Optionally, on
  `pointerenter`/`focus` of a switch link, also `document.fonts.load()` the target language's faces (the chunk is
  already prefetched there), so the swap happens before the click.
- **Verify:** `qa/qa_i18n.mjs switch --engines webkit --vps 390` should give 20/20; `qa/probe.mjs webkit` should show
  the same top at 30 ms and 2 s.

### I2 (P2, owner decision): link previews ignore `?side` and `?reception`

- **Where:** pre-rendered `dist/{lang}/index.html`. `config.prerender.sideShells` is false (O7).
- **Seen:** WhatsApp, Telegram and iMessage previews read only the static HTML. So `/bn/?side=bride&reception=0`
  previews as "অক্ষয় ও শ্রেয়া · শুভ বিবাহ / শুভ বিবাহ · ২৫, ২৬ ও ২৯শে নভেম্বর · কলকাতা · সহরসা". That is groom
  first, and it names the 29th and Saharsa to guests whose link hides the Reception. The client head is right once
  the page runs (16/16). This contradicts "`?reception=0` hides the 29 Nov Reception" only at the preview, but the
  preview is the first thing a guest sees.
- **Fix (pick one):**
  - (a) Pre-render variant shells (`/{lang}/b/`, `/{lang}/r0/`, `/{lang}/b/r0/`, or `?`-free aliases that set the
    variant) with their own head. Share those URLs.
  - (b) Make the default description date-neutral for the shared head, for example the heading plus Kolkata only.
    This is an owner copy choice.
  - (c) Document in the README that `reception=0` links must be shared without a preview.

### I3 (P3): after a switch on a phone the bar hides at once

- **Where:** `src/components/chrome/TopBar.tsx`, scroll handler.
- **Seen:** the restore scroll counts as "scroll down". Chromium 390 has `data-hidden` 150 ms after every switch,
  and WebKit has it on Closing. The guest who just tapped `বা` sees the bar (and the switch) slide away and must
  scroll up to switch again or to check.
- **Fix:** on `lang` change, set `lastY.current = scrollY` after the restore and keep `hidden=false`. Or ignore
  scrolls within 300 ms of `restorePlace()`/`jumpTo()` (the same `lastJump` idea `LangLayout` already uses).

### I4 (P3): native-script language paths go to English

- **Where:** `src/lib/langs.ts` `ALIASES`, `public/redirect.js`, the README nginx block, `_redirects`.
- **Seen:** `/हिन्दी`, `/हिंदी`, `/मैथिली` and `/বাংলা` (as typed or shared) all land on `/en/` in every engine and
  on both hosts. The spec only lists Latin aliases, so this is not a contract breach. But a Bengali guest typing
  "বাংলা" gets English.
- **Fix:** add these aliases: हिन्दी, हिंदी -> hi; मैथिली -> mai; বাংলা, বাঙলা -> bn. `normalizeLang` already
  decodes the URI. Add the 301s to nginx/_redirects too (percent-encoded).

### I5 (P3): the no-JS 404 is English-only and does not keep the language

- **Where:** `NotFound.tsx` / `dist/404.html`.
- **Seen:** without JS, `/bn/deep` shows the 404 shell (`<html lang="en">`) with 4 endonym links. The guest must pick
  বাংলা again. With JS, it redirects to `/bn/` correctly.
- **Fix (optional):** `redirect.js` cannot run without JS. Add `<noscript>` links that keep the first segment, or add
  host rules `/{lang}/* -> /{lang}/` (302) to nginx/_redirects/vercel/netlify so the path is fixed by the host.

### I6 (INFO, latent): the venue/address Noto subsets miss a few letters the copy uses elsewhere

- Noto Serif Devanagari 500/600 lack ऊ घ ङ, and Noto Serif Bengali 500 lacks ঘ. Today these letters appear only in
  strings set in other faces: ऊपर (`nav.top`), घंटा/घंटे and ঘণ্টা (countdown), मङ्गलं (shloka). CDP confirms that
  nothing falls back, so there is nothing to fix now.
- `check-budget.mjs` checks coverage per language (the union of faces), not per face. So a future venue/address
  edit with घ would mix two faces inside one word without failing the build.
- **Suggestion:** when the copy changes, re-run `npm run assets:fonts`, or make the gate check each face's
  `textFrom` strings against that face's cmap.

### I7 (INFO): head details for the owner

- `og:locale` `mai_IN` (and `mai_IN` in the alternates) is probably not a locale Facebook recognises. I have not
  verified this against Facebook's list. Crawlers ignore unknown values, so it is harmless. `hi_IN` would be the
  closest fallback if a preview tool complains.
- `hreflang` and `canonical` are omitted until `VITE_SITE_URL` is set (O10, the build says so). Set it before
  hosting so each language page names its siblings.
- The root shell and `404.html` say `<html lang="en">` with the English title. That is fine: they redirect at once.

### I8 (INFO): small observations, no action needed

- After the wedding start, `/{lang}/#countdown` lands on Celebrations but the URL keeps `#countdown` until the guest
  scrolls (then the hash sync rewrites it).
- The Tirhuta flourish is an SVG of outlines (`aria-hidden`, `data-text="मिथिला"`), so it has no `lang="mai-Tirh"`
  as spec 4.6 says. That is moot for outlines; update the spec line. It still reads "मिथिना"/"মিথিনা" to Devanagari
  and Bengali readers at heading size (QA F15, native review).
- Metric-override fallback faces (`* Fallback`, `local()` sources) report `status: error` in Linux Chromium, where
  those local fonts do not exist. This is expected and does no harm (no text uses them once the web fonts load).

## Harness notes (not site defects)

- WebKit `page.goto(..., {waitUntil: 'load'})` timed out once on nginx for a percent-encoded Devanagari path. A
  direct probe shows it redirects to `/en/` in WebKit and Chromium: the replace happens before `load`.
- WebKit iPhone emulation, `/en/#footer`: the footer is in view but `innerHeight + scrollY < scrollHeight` (dynamic
  toolbar inset), so the "at end" test misread it. `/bn/#footer` passed.
- An earlier phone switch run failed with "element is outside of the viewport". That is by design (the bar hides on
  scroll down, spec 2.3.8). The probe now scrolls up a little before tapping, as a guest would.
- The hash sync only starts after real user input (`userScrolled`), so a scripted `scrollTo` and then a wheel event
  in the same section does not write the hash. That is correct behaviour.
